\title{MachBoost: Speculative Decoding from Local Context for On-Device LLMs}
\author{Vistrit Pandey\\\texttt{vistrit@blinkfire.com}}
\date{July 2026}

\begin{abstract}
Autoregressive language model inference is slow in a very ordinary way: for most decoders, one generated token still means one more target-model step. Speculative decoding can reduce that serial work, but many practical variants require a draft model, modified model heads, or serving infrastructure that is awkward for local use. This paper explores a smaller question: when a local task is already grounded in nearby text, can that text itself draft useful continuations? MachBoost answers yes for a narrow but common class of workloads. It indexes prompt and local-context tokens, proposes n-gram continuations, and verifies them with the target model before committing any generated token. On an Apple M1 Max with 32 GB memory, using MLX and \path{mlx-community/Qwen3.5-0.8B-MLX-4bit}, MachBoost reaches a 1.38$\times$ median speedup across 35 runs with token-for-token agreement against serial greedy decoding in every run. The gains are concentrated where they should be: policy, JSON, and code-continuation fixtures reach 1.60--1.62$\times$ median speedups, while open-ended controls slow down. The system therefore includes a small benchmark-and-disable step rather than pretending the method is universal.
\end{abstract}

\section{Introduction}
Running LLMs on a laptop has become realistic, but it has not made autoregressive decoding disappear. A small model on Apple Silicon may fit in memory and still feel slow because the loop is serial: produce a token, update the prefix, run the model again. That bottleneck is especially visible in developer workflows, where the model often sits inside an editor, command runner, notebook, or local assistant.

Speculative decoding offers a way around part of this loop. A cheap source guesses several future tokens; the target model checks the guess; accepted tokens are emitted without paying for one full target step each. Prior work usually gets the draft from another model, extra heads, or a reference sequence. MachBoost takes the reference idea and applies it to the local machine. If the user is asking about a repo, config, note, policy, or retrieved passage, the likely continuation may already be present in that local text.

The scope is deliberately modest. MachBoost does not try to accelerate every prompt. It tries to accelerate grounded prompts without changing the target model's greedy output. If the local text is unhelpful, the method can be slower; the implementation exposes that fact through measurement and falls back to the serial path.

This paper makes four concrete contributions:
\begin{itemize}[leftmargin=*]
  \item a local-context drafter that proposes continuations from prompt text, files, and retrieved material;
  \item verifier-backed generation for MLX and Hugging Face-style runtimes, including a fix for a cache-path divergence observed in MLX;
  \item a Python API that measures a workload before deciding whether to use the boosted path;
  \item an Apple Silicon evaluation with 35 MLX runs, 100\% token agreement, and a 1.38$\times$ median speedup overall.
\end{itemize}

\section{Background and Related Work}
Speculative decoding was introduced as a way to accelerate autoregressive transformer inference without changing outputs by drafting candidate tokens and verifying them in parallel with the target model \cite{leviathan2023speculative}. Speculative sampling independently developed a related draft-and-verify method for sampled decoding and reported 2--2.5$\times$ speedups in a distributed setting \cite{chen2023speculative}. Subsequent work explored architecture-level or self-drafting variants. Medusa adds multiple decoding heads to predict future tokens and verifies candidate trees \cite{cai2024medusa}.

MachBoost is closest to methods that exploit references or prompt overlap rather than an auxiliary draft model. LLMA observes that outputs in retrieval and reference-grounded scenarios often share spans with the input reference, then verifies copied spans to preserve greedy output \cite{yang2023llma}. Prompt Lookup Decoding replaces the draft model with n-gram matching over the prompt \cite{saxena2023promptlookup}; PLD+ extends that idea by using language-model artifacts such as attention or hidden states to rank candidate spans \cite{somasundaram2024pldplus}. MachBoost differs mainly in packaging and operating assumptions: it treats local files and retrieved snippets as ordinary inputs to the accelerator, keeps benchmark data machine-readable, and makes low-overlap prompts a measured fallback case rather than an error.

The implementation targets common local inference stacks. Hugging Face Transformers provides the broad model API surface for Python inference \cite{wolf2020transformers}. MLX is an Apple Silicon-oriented array framework and runtime used here for Mac-native evaluation \cite{mlx2023}. Our measurements use a Qwen-family model converted for MLX; Qwen3 is the relevant public model-family report \cite{qwen2025qwen3}.

\section{Problem Setting}
Let $M$ be a target autoregressive model and let $x$ be the prompt token sequence. Greedy decoding emits
\[
  y_t = \arg\max_v M(v \mid x, y_{<t})
\]
for each generation step $t$. MachBoost receives a corpus $C$ derived from prompt text, retrieved context, local files, or user-provided strings. The goal is to reduce wall-clock latency while returning the same sequence $y$ that greedy decoding with $M$ would return.

This paper stays with greedy decoding. Sampling-compatible speculative decoding is possible in principle, but greedy argmax verification gives a simple correctness check: the accelerated sequence must match the serial baseline token-for-token.

\section{Method}
The implementation has three moving parts: a drafter, a verifier, and a decision rule for whether to use the drafter on a workload.

\subsection{Drafting from Nearby Text}
The drafter indexes token n-grams from a corpus $C$. At generation time it looks at the current prefix $p = x \Vert \hat{y}$, searches for suffixes of $p$ that occur in $C$, and proposes the tokens that followed the best matching span. Longer suffix matches are preferred, with draft length as a secondary signal. The design is intentionally plain: no learned draft model, no training step, and no hidden state from the target model.

\subsection{Verification Against the Target Model}
Given a prefix $p$ and draft $d=(d_1,\dots,d_k)$, the verifier checks how many draft tokens are equal to the target model's greedy continuation. For verifier-capable runtimes, this can be done by scoring $p \Vert d$ in a single target call and comparing target argmax tokens at the relevant positions. If the first $a$ draft tokens are accepted, they are committed. If a residual target token is available at the first mismatch, it is emitted to preserve progress. Otherwise the system falls back to a normal target step.

The invariant is:
\[
  \mathrm{Boost}(M,x,C,T) = \mathrm{Greedy}(M,x,T)
\]
for a maximum generation length $T$. In the implementation, every benchmark row records an \texttt{output\_match} flag by comparing boosted and baseline token IDs directly.

\subsection{Keeping the Cache Path Stable}
One engineering detail turned out to matter more than expected. In MLX, extending a prompt cache token-by-token is not always numerically identical to rebuilding a long prefix in a single call. During testing, a non-trimmable cache could partially accept a draft, rebuild after rejection, and later choose a different argmax than the serial cache path.

MachBoost handles this by verifying drafts on a cloned trial cache when the runtime supports cloning. Fully accepted drafts commit the trial cache. On partial rejection, if the trial cache cannot be trimmed safely, only the accepted tokens are advanced on the live cache. The rejected tail is never allowed to pollute the future prefix state.

\subsection{Deciding When to Use the Drafter}
Drafting from local text is sometimes the wrong choice. Open-ended prompts often accept only a few draft tokens, so verification overhead dominates. MachBoost therefore exposes a benchmark step. For a prompt family, it measures:
\begin{itemize}[leftmargin=*]
  \item token match between baseline and boosted output,
  \item wall-clock speedup,
  \item accepted draft tokens divided by generated tokens,
  \item target-call or forward-call reduction.
\end{itemize}

The high-level API can then calibrate an accelerator:
\begin{verbatim}
from machboost import Accelerator, GatePolicy

boost = Accelerator.from_mlx(model, context_paths=["./docs", "./src"])
calibration = boost.calibrate(
    prompts,
    max_tokens=32,
    gate_policy=GatePolicy(min_speedup=1.05,
                           min_acceptance_rate=0.10),
)
text, stats = boost.generate(prompt, max_tokens=128)
\end{verbatim}

If the measured workload fails the policy, \texttt{generate} uses the serial baseline path. This is not as exciting as always-on acceleration, but it is much safer for a package people may drop into arbitrary local workflows.

\section{Implementation}
MachBoost is implemented as a small Python package with no required runtime dependencies. Optional extras install backend-specific dependencies:
\begin{itemize}[leftmargin=*]
  \item \texttt{machboost[mlx]} for MLX and \texttt{mlx-lm},
  \item \texttt{machboost[hf]} for PyTorch and Transformers,
  \item Ollama HTTP support for benchmarking and capability detection.
\end{itemize}

The core package defines a \texttt{StepService} protocol with \texttt{next\_token(prefix)} and an optional \texttt{verify(prefix, candidate)} hook. A service with only \texttt{next\_token} can still run through the wrapper, but it cannot skip target work. A service with \texttt{verify} can accept several draft tokens per target call. The high-level \texttt{Accelerator} API loads MLX or Hugging Face models, reads strings, files, or directories as context, and exposes \texttt{benchmark}, \texttt{calibrate}, and \texttt{generate}. The Ollama HTTP adapter is intentionally limited: the public API does not expose token IDs, logits, KV-cache snapshots, or verifier hooks, so it is useful for benchmarking and option management but not for this form of acceleration.

\section{Evaluation}
\subsection{Setup}
We evaluate on a Mac with Apple M1 Max, 10 CPU cores, 32 GB unified memory, and macOS 26.5.2. The Python environment includes MLX 0.31.2 and \texttt{mlx-lm} 0.31.3. The evaluated model is \path{mlx-community/Qwen3.5-0.8B-MLX-4bit}. All results come from \path{results/mlx_evidence_suite_20260701.json}.

The suite contains seven fixture families with five fresh nonce-bearing repeats each: policy continuation, structured JSON continuation, retrieval-style answering, code completion, repository command quote, creative open-ended generation, and short answer. Each run generates up to 24 tokens. The positive fixtures are designed to have real local-context overlap; the creative and short-answer fixtures are negative controls.

The per-fixture view is more informative than the aggregate number. Policy, JSON, and code continuation all exceed 1.60$\times$ median speedup. Repository quote is weaker but still useful at 1.38$\times$. Retrieval-style answering improves only 1.12$\times$; the local text helps, but fewer tokens are accepted per verification call. The negative controls are a useful sanity check: they still match the baseline, but they are slower. Their continuations are not mostly recoverable from the provided context, so the extra verifier calls are wasted.

\subsection{Interpretation}
These results are not evidence for a universal speedup layer. They instead suggest that grounded local workloads are separable from open-ended ones with a small amount of measurement. That distinction matters for developer tools. A repo assistant, config editor, policy search tool, or command helper can benchmark representative prompts once and avoid using the drafter where acceptance is low.

\section{Limitations}
The evidence here is still early. The main benchmark uses one small MLX model on one Apple Silicon machine with 24-token generations. It does not yet answer how the method behaves on 3B/8B models, long outputs, sampled decoding, or large real repositories. The drafter is also deliberately simple; unlike PLD+, it does not rank spans with model artifacts. The Hugging Face adapter exists at the package level, but the reported suite focuses on MLX because that is where the cache work has been exercised most. Ollama over HTTP remains outside the accelerated path unless the runtime exposes a native verifier hook or a patched runner.

There is also a methodological limit. Token equality is a strong check for greedy decoding, but it says little about semantic quality under sampling. For that reason, this paper makes no quality claim. The goal is lower latency when the desired output is the same.

\section{Future Work}
Several next steps are straightforward. The evaluation needs larger models, longer generations, and real workspaces. The drafter could use suffix automata, prompt/document segmentation, model-artifact ranking, or retrieval over multiple corpora. The decision rule could also become online: try the drafter for a short prefix, back off when acceptance is low, and re-enable it inside structured regions. Finally, a native Ollama or llama.cpp verifier hook would make the approach available to many more local users.

\section{Conclusion}
MachBoost is a practical experiment in using nearby text as the draft source for speculative decoding. It is not a shortcut for every prompt. On the measured MLX suite, however, it matches serial greedy decoding across all 35 runs and reaches a 1.38$\times$ median speedup overall, with 1.60--1.62$\times$ speedups on the strongest grounded tasks. The package design reflects the main lesson from the results: use the drafter when local context predicts the next tokens, and fall back when it does not.
